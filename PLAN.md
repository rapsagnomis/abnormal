# (a/b)normal — Plan

Desktop tool to analyse and compare the sonic characteristics of a song against a reference track.

## Decisions
- **Platform:** native desktop, Tauri v2 (Rust core + React/TypeScript UI)
- **Comparison:** 1:1 (track A vs reference track B), full song or selected regions
- **Stereo analysis:** yes
- **Tonal suggestions:** concrete EQ moves (type, freq, gain, Q)
- **Formats:** mp3, flac, wav

## Architecture

```
┌─────────── React UI (TypeScript) ───────────┐
│ drop zone · 2× canvas waveform (Rust peaks) │
│ transport · regions · uPlot charts · A/B    │
└──────────────┬──────────────────────────────┘
               │ Tauri commands + events (playhead, progress)
┌──────────────▼──────────────────────────────┐
│ Rust core                                   │
│  decode   : symphonia → f32 planar buffers  │
│  playback : cpal stream, A/B crossfade,     │
│             loudness-match gain, seek, loop │
│  analysis : rayon workers per track/region  │
│    loudness ─ ebur128 (I, S, M, LRA, dBTP)  │
│    dynamics ─ crest, PSR, TT-DR, histogram  │
│    tonal    ─ realfft LTAS, 1/6-oct smooth  │
│    stereo   ─ correlation, M/S, width/band  │
│  suggest  : diff curve → EQ moves           │
└─────────────────────────────────────────────┘
```

- Audio is decoded once and stays in Rust; the UI only receives downsampled peaks and analysis results.
- All analysis takes a `(track, start, end)` range — whole song = `0..len`, so region comparison is the same code path.
- Playback is a single cpal stream: A/B switch is a short crossfade, loudness-match is a gain derived from the integrated LUFS difference, optional playhead lock between tracks.

## Metrics

| Area | Measures |
|---|---|
| Loudness | Integrated LUFS, short-term/momentary curves, LRA, sample peak, true peak (dBTP), PLR |
| Micro dynamics | Crest factor and PSR over time, peak-vs-RMS histogram, transient strength |
| Macro dynamics | LRA, short-term loudness distribution, TT-DR score, section contrast |
| Tonal | Loudness-normalized LTAS (1/6 oct), band energies (sub → air), spectral tilt, centroid, A−B diff curve |
| Stereo | Correlation over time, M/S ratio, width per band, goniometer for selected region |

**EQ suggestions:** smooth diff curve → find contiguous deviations above ~1 dB → fit to shelf/peak (f, gain, Q) → rank by perceptual weight.

## Phases
1. **Skeleton** ✅ — Tauri + Vite + React scaffold, drag & drop 1–2 files, symphonia decode, waveform peaks → custom canvas waveform (wavesurfer dropped: it is built around an HTML media element, but playback is native), cpal transport (play/seek/loop region), A/B switch.
2. **Loudness** ✅ — ebur128 integration (mono measured as dual mono), M/S curve overlay, loudness-matched A/B (attenuate the louder track, never boost), full-track vs selection stats, validated against EBU Tech 3341/3342 signals and cross-checked with ffmpeg. Also: waveform zoom/pan with on-demand detail peaks.
3. **Dynamics** ✅ — crest factor (whole + 50 ms median), PSR (median/min + gated curve overlay), onset rate and attack rise, TT DR (matches ffmpeg drmeter within 0.05), short-term P10/P50/P95, short-term loudness and crest distributions (A/B overlaid histograms). Curve + Match controls moved to the transport bar.
4. **Tonal + stereo** ✅ — loudness-normalised LTAS (energy per 1/6 oct, pink = flat), A−B difference, centroid, tilt, 7 band levels; correlation (mean, worst 5%, % out of phase, curve overlay), side/mid, L/R balance, width per band and per frequency, goniometers. Waveform simplified to a single min/max layer; Link off by default.
5. **Region compare + suggestions** ✅ — every tab measures full tracks or selections (a lane without a selection falls back to its full track; load the same file twice to compare two parts of one song); "EQ match" tab fits up to 6 bell/shelf moves for A towards B (1/3-oct smoothed, median level offset removed, Q ≤ 2, ±6 dB, ≥ ½ oct apart) with needed-vs-suggested chart and copy; report export as Markdown or JSON summary (later removed).
6. **Library matching** ✅ — every mp3/flac/wav under `~/Music/albums` is analysed in the background (≤ 4 workers, decoded audio is held in memory) into a JSON database in the app data folder; each start re-scans and only analyses new/changed files (size + mtime), dropping deleted ones; failures are stored so they aren't retried until the file changes. Fingerprint per track: 1/3-oct spectrum shape (32 Hz–16 kHz, mean removed; lossy files are low-passed above), dynamics (LRA, PLR, PSR, 50 ms crest, DR, log onset rate, attack rise) and stereo (correlation, width per band). Distance = RMS of z-scores, each value scaled by its spread over the library, per group, combined 0.5/0.3/0.2 (or one group alone); score = 100·e^−d. "Similar" tab lists the top 30 for A or B (full track or selection), with per-aspect scores and load-into-A/B.
7. **Listening & structure** ✅ — *EQ audition*: the suggested moves (each switchable in the EQ tab) play on A through RBJ biquads in the player (TDF-II, f64, always running so on/off is a 15 ms crossfade), level-compensated by the K-weighted loudness change estimated from A's spectrum; trims never boost (if compensation would, both tracks come down). *Spectrogram* lane display (S): STFT 4096, log rows 30 Hz–20 kHz as energy per ⅓-oct equivalent (pink = flat), bytes over raw IPC, whole-track overview then screen-resolution detail per view; each track scaled to its own ceiling (99.8th percentile, 66 dB range). *Sections*: 0.5 s cells of timbre (octave bands) + chroma + level, z-scored with spread floors, Foote checkerboard novelty (8 s half-width, scaled to mean across-minus-within distance, peaks ≥ 0.15 and ≥ 8 s apart), grouped by distance between section means (< 0.6 × median); shown as a clickable strip under each lane (Shift+click extends). *Where it matters*: half-octave band levels per 0.5 s relative to the surrounding 3 s (`activity.rs`); each EQ move gets a ▶ that loops the 4 s of A where its range is furthest from B's median in the direction it corrects. (A separate Masking tab — heat map, crowded/thin lists — was tried and dropped as too complicated for what it told you.) Shared STFT helper in `stft.rs`.
8. **Library + Deezer downloads** ✅ — "Similar" became the "Library" tab (same matches view); its search box now lists library hits (first 8, "Show all") and Deezer tracks below, each with ↓ Track / ↓ Album buttons that download FLAC into `~/Music/albums`. Downloads go through Deemix without its window (`deemix.rs`): the Deemix app's bundled server is run with its own Electron binary in Node mode (`ELECTRON_RUN_AS_NODE`), headless, single-user, on a free local port, with `DEEMIX_DATA_DIR` pointing inside our app data so the GUI's queue and login are never touched and it works whether or not the GUI is open. Its config is the GUI's `config.json` copied on each start, download folder forced to the library. The Deezer ARL is pasted once in the tab and saved by Deemix itself (single-user mode), which hands it back on `/api/connect` for auto-login; we never store it. A watcher thread polls the queue while anything is pending (`deezer-queue` event) and rescans the library when a download finishes. The server is killed on exit; a stale one from a crash is killed via its pid file. Also: the EQ match tab was folded into Tonal, under the spectrum charts.
9. **Library display** ✅ — copies of the same audio (identical fingerprint, `Features::identity`; the library had 745 such copies across playlist folders) are folded into one entry in search and matches, with the other paths listed, and copies of the matched track are left out of its matches. Deezer results drop the same recording on several releases (artist + title + length within 2 s). Rows show album art, "Title – Artist" and the album, falling back to file name and folder. Tags are read by probing only (`decode::read_tags`, no decoding), stored per entry (`meta`, read lazily for entries indexed before, so no `DB_VERSION` bump); covers come from the embedded front cover or the folder's `cover.jpg`, saved as 128 px JPEG thumbnails named by image hash in `covers/` next to the database (one per album) and shown through Tauri's asset protocol (scope `$APPDATA/covers/*`). Search also matches title, artist and album.
10. **Song structure (All-In-One)** ✅ — tempo, beats, bars and labelled parts (intro, verse, chorus, bridge, inst, solo, break, outro) from [All-In-One](https://github.com/mir-aidj/all-in-one), run in a private Python env the app sets up on request (`structure.rs`: `uv` venv in `<app data>/allin1`, Python 3.11, torch 2.4.1, madmom from git, allin1 1.1.0 with `--no-deps`; ~0.9 GB with model weights). NATTEN, which allin1 imports, is not installed: 0.17.x crashes on import without CUDA and later releases dropped the functions allin1 uses, and its macOS CPU kernels are slow. `natten_shim.py` reimplements the four functions in plain PyTorch (checked against NATTEN 0.15.1 to <1e-6, and the full ensemble gives identical results); on CPU it is >10× faster than NATTEN's kernels (1.8 s vs ~24 s per model), on MPS it's slower, so the runner separates stems with Demucs on the GPU and runs the 8-model ensemble on CPU: ~35 s for a 3-minute song (vs ~220 s stock). Results are cached per file (path, size, mtime); one job at a time; requested on load. Lanes show labelled parts (consecutive phrases with the same label merged) and BPM; clicking a part selects it and the same occurrence of that part in the other track, so every tab compares like with like. Dynamics tab: per part type, loudness relative to the track, width and tilt, A vs B. The old timbre/chroma sections remain the fallback before setup or while analysing.
    *Refinements:* Demucs runs with `--overlap 0.1` (default 0.25; ~2 s faster, identical structure). Each job is two processes, stem separation then the model, each stage with its own worker, so a queued second track separates while the first's model runs (pair: 62 s vs ~70 s sequential; less than hoped because Demucs also uses CPU). A 4-model ensemble was tried on 7 library tracks: 95 % of song time got the same label as 8 models but 4 of 7 tracks differed somewhere (bridge vs solo/break, an outro 12 s early, beats on one), for ~7 s saved, so the 8-model ensemble stays. Without Demucs (the mix as all four stems) beats survive (97 %) but parts collapse to "chorus". *Editing:* drag the border between two parts (snaps to the nearest bar within 10 px, Alt to place freely), click a selected part (or double-click) to rename it (intro / verse / chorus / bridge / outro / other), "Reset to detected" in the same picker. Corrections are stored per file in `allin1/edits/`, keyed without the results version, and override the detected parts everywhere (strip, like-for-like selection, per-part table).
11. **Pro-Q 4 export** ✅ — the EQ match's Copy button now puts a FabFilter Pro-Q 4 preset on the clipboard (the same INI-like text as its .ffp files, which its instance menu pastes) (`src/lib/proq.ts`, `pro_q_template`). A "Save to Pro-Q 4" button that wrote the preset into Pro-Q's preset folder was later removed: copy and paste is enough. Encodings, read off Pro-Q 4's own presets: frequency = log2 Hz, gain in dB, Q normalised log over 0.025–40 (Q 1 = 0.5), shape 0 bell / 1 low shelf / 3 high shelf, placement 2 = stereo; 24 band slots. Everything except the bands comes from the user's "Default Setting" preset when there is one (so analyser/display preferences carry over), else from Pro-Q's defaults; bands are static (dynamics and spectral off). Shelves are RBJ Q 0.707 and their frequency is the mid-slope point, as in Pro-Q.
12. **Mid/side EQ match and full match (Matchering ideas)** ✅ — the EQ match is computed in Rust from both tracks' ranges (`match_eq`, replacing `suggest_eq`) using mid and side spectra on the shared grid (`spectrum::mid_side`). The stereo moves are fitted as before (to the combined spectrum); what is left of the side's difference (B − A side, same level offset, minus the stereo moves) becomes a *width* change (median over 150 Hz–10 kHz, ≥ 0.5 dB, shown as "Side level" and exported as a Side high shelf at 10 Hz) and up to 3 *side-only* moves, fitted with the same greedy fitter, weighted down where A's side is more than 6 dB below its mid (none below −24 dB). Moves carry a `placement` (stereo/side): the player runs side stages on (L−R)/2 only, Pro-Q 4 export uses Stereo Placement 4 (Side; 3 is Mid, 0/1 Left/Right, read off Pro-Q's factory presets). *Full match*: [Matchering](https://github.com/sergree/matchering)'s unconstrained correction (no GPL code used: reimplemented from its description), i.e. the raw B − A difference per grid point, offset removed, smoothed by LOWESS (local linear, tricube, 3/8 octave like Matchering's 3.75 % of a 10-octave axis), limited to ±12 dB (Matchering is unbounded); drawn on the tonal and side correction charts, with the RMS gap to the moves. Matchering averages magnitudes over 4096-point boxcar frames, we use the existing power PSD. *Hear the full match*: A's playback buffer is rendered offline through linear-phase FIRs (`fir.rs`: zero-phase spectrum from the curve → inverse FFT → centred, Hann-windowed, ~6 Hz resolution, 8192 taps at 48 kHz; overlap-add FFT convolution of mid and side, delay removed) into a sample-aligned alternate buffer that the player crossfades to (Audition: Moves | Full match). A render generation counter drops stale renders; loading a track drops its alternate. Level compensation for both kinds is estimated from A's spectrum split into mid and side shares. *Loudest parts only*: Matchering's gating, the range cut into equal pieces of ≤ 15 s and only pieces with mid power ≥ the mean over pieces measured.
13. **Export A matched** ✅ — the export button next to EQ in the transport bar writes A as WAV at its own sample rate (`export.rs`, `export_track`), with the EQ match as auditioned (the switched-on moves as biquads, side moves on L − R, or the full match's linear-phase mid/side FIRs) and/or its loudness matched to B. Levels are measured on the rendered result over the same ranges as the match: EQ alone keeps A's integrated loudness (exact, rather than the playback's spectrum-based estimate), loudness match lands on B's, and unlike playback it may boost. 24-bit PCM clipped at full scale (the status line reports the peak), or 32-bit float to keep overs. Mono stays mono.
14. **Extra tracks (C, D)** ✅ — a + button after the A/B switch adds up to two more lanes to listen to (one at a time, like A and B). The engine has 4 fixed slots (`SLOTS = 4`); the UI keeps the extra lanes' engine slots in display order, so labels (and colours) follow position: removing C (hover − on its switch button) unloads that slot and D becomes C with no audio moved. Tab / Shift+Tab cycle through loaded tracks in lane order, 1–4 pick one. Loudness match brings every loaded track down to the quietest; linking, selections, song-part selection and zoom cover all lanes. Analysis tabs, the EQ match and export stay A vs B. Lanes open/close by transitioning their grid row from 0fr, switch buttons by width.
    *Later:* up to 8 tracks in all (A–H, `SLOTS = 8`); lanes keep at least 150 px and the lane list scrolls; the switch buttons narrow past four tracks. Loudness Match, EQ and Export moved to the top bar (`MatchControls`).
15. **Compared pair** ✅ — with more than two tracks, analysis stays one-to-one between a *track* and a *reference*. The reference is pinned (B by default; the pin button on any lane, or the panel's picker, moves it; pinning the current track swaps the two). The track follows whatever is being listened to, except the reference itself, so tabbing through C, D, E… compares each with the reference. (A Follow/Locked toggle to freeze it was tried and removed: always following is simpler.) Every tab, the EQ match (`match_eq` takes the pair's slots), EQ audition and its level compensation, the full-match rendering, Export (`export_track` takes the pair's slots), song-part stats, the Library's "Like"/"Load" buttons follow the pair, labelled with its real letters and drawn in its lanes' colours. A new pair drops the old EQ match immediately so it is never auditioned on the wrong track; the previous track's EQ and full-match rendering are cleared. Lanes show "vs" / "Ref" chips once the pair isn't plain A vs B, and lanes outside the pair are dimmed a little. Loudness Match still levels every loaded track.
    *Layout:* the top bar is the comparison — title | `Compare [C] vs [B]` │ Loudness Match, EQ │ Export (centred, in the pair's colours) | output status; the pair picker moved there from the panel and is always shown. The bottom bar is playing and viewing — playback (⏮ −5s ▶ +5s, Loop) | listen to (A B C … +) | view (Wave/Spec, Curve, Link) | volume. The panel keeps only tabs and Full/Selection.
    *Track controls:* a `[− +]` stepper before the A B C … switch, with playback and tracks anchored left (view and volume right), so adding and removing always happen at the same spot; − closes the last extra lane, the hover − on a button closes that one. Removal is debounced (clicks while a lane is closing are ignored), and the switch doesn't narrow its buttons while the pointer is over it.
16. **Feedback & motion, tier 1** ✅ — buttons ease between states (140 ms) and give slightly when pressed; one "working" sweep for anything running: under a lane's header while it decodes or is measured (in its colour), on the EQ button while the match is fitted or the full match rendered (on but not heard yet), on Export while writing; pending table values pulse instead of sitting dimmed, "Fitting…"/"Rendering…" notes pulse. 17. **Overview first** ✅ — each analysis tab opens with three headline cards (`HEADLINES` in `metrics.ts`, `HeadlineCards.tsx`): big numbers for both tracks in their colours, Δ below, warnings in red; the table below no longer repeats them. Loudness: Integrated, True peak, PLR. Dynamics: PSR median, DR, LRA. 18. **Live feedback** ✅ — *level meters*: the mixer records each track's peak per audio buffer (after trim and EQ, before the A/B switch and volume, so every track is metered though one is heard), returned with `transport` (polled every frame); each track button has a thin meter on its right edge (−48…0 dBFS, instant attack, 30 dB/s release, red near 0). *Live analyser*: while playing with the Tonal tab open, `live_spectrum` (~15×/s) measures the ~0.4 s up to the playhead of the track being heard (one 16k FFT on the shared grid, normalised by its integrated loudness like the long-term spectrum) and the Spectrum chart draws it as a lighter "Live · X" curve, kept out of the y range so the axes stay put. *Waveform sweep-in*: a newly loaded track is revealed left to right (clip-path, 650 ms). *Curve morph*: changing Curve mode (or a curve appearing/going away, or a new track) bends the overlay from the old shape into the new over 380 ms on a common pixel grid while grids and labels cross-fade. Scale labels over the lanes (curve grid, spectrogram frequencies) sit on dark chips so the waveform and curves no longer run through them.
    *Keys:* tracks are picked with the number row by physical position (`e.code` Digit1–8, so & é " ' ( § è ! on AZERTY, 1–8 on QWERTY; Digit0 = à fits the view); Tab switches between the compared pair only (analysed track ⇄ reference).
19. **Display** ✅ — switching Wave ⇄ Spec cross-fades (a snapshot of the old display on a second canvas fades out over the new, 320 ms). The spectrogram uses an inferno-like ramp (indigo → purple → red → orange → yellow → white) instead of one blue hue: lightness still rises steadily, and the turning hue makes neighbouring levels distinguishable. (The waveform was briefly shaded by spectral brightness; dropped with the bar display below.)
    *Waveform as bars:* rounded vertical bars on a fixed screen grid (3 px wide, 2 px apart, CSS px), each as tall as the peak (max of |max|, |min|) of the time it covers, mirrored about the centre line, never shorter than a round dot; one colour, the lane's (muted when not heard). A bar takes every bucket it touches (partial ones included, so peaks don't flicker while zooming), preferring detail peaks; on zoom, pan or finer data the bars ease to their new heights (160 ms) in the same animation loop as curve morphs. Tried and dropped before it: per-pixel min/max columns, an RMS body with peak halo, an amplitude-density rendering, a smooth peak-held outline, and brightness shading.
    *Library:* every library/Deezer row also has "+ New": loads into the first empty lane, or opens a new one (up to H), via a `LoadNewContext` from the panel (its tooltip names the lane it would use).
    *Library motion:* result rows rise in with a short capped stagger; re-ranked matches glide to their new places (FLIP, `useFlip`) and their scores count; shimmering skeleton rows replace "Searching…"; Load/+ New ring the button and tint the row; download buttons fill as they progress (`@property --progress`) and "✓" pops in; the scan bar fills smoothly; tab content and search ⇄ matches fade in. *Pair emphasis:* the analysed lane gets a 6 px bar and stronger tint, the reference a 3 px bar and a faint one.
    *Bars as cursor and scale:* the playhead is light sliding along the bars: the canvas leaves out the bars within three of it, which are drawn as live elements instead: each is dilated or squeezed towards the playhead's fixed height (80 % of the lane) by a falloff of its centre's distance to the exact playhead position — steep ahead of it (σ 0.55, cubic: bars snap into shape as it arrives, no slow wave front), gentler behind (σ 1.1, Gaussian), and lit (lighter, up to 2 px wider, glow) by a tighter one (σ 0.45); recomputed every frame (the canvas only redraws when the playhead crosses into another bar), so brightness and size pass smoothly from bar to bar instead of jumping (the thin line remains on the spectrogram); the bar under the pointer lifts slightly and lightens, less than the playhead. Faint vertical time guidelines sit behind the bars at every ruler tick, with finer subdivisions fading in as zooming makes room (6 → 24 px apart); ruler steps now go down to 10 ms.
    *Selection on the bars:* like the playhead, the selection (and the loop it sets) is shown on the bars: bars inside it are lit (`--wave-selected`), bars straddling an edge by how much of them is inside (eased), so the edge moves smoothly while dragging; with a selection, the other bars drop to half opacity. The overlay band is now faint (edges only); on the spectrogram, which has no bars, it keeps its clear tint.
    *Loop per selection:* the Loop button is gone; looping is per track (`loop_enabled` per slot in the engine, `set_loop_enabled(slot, …)`, `Transport.loopEnabled[]`).     *Curve labels in their own strip:* with a curve shown, a 34 px strip at the right of each lane holds its scale labels alone — bars, the curve, its grid lines and reference line stop before it (the playhead/hover bars too), and on the spectrogram the strip gets a dark backing — so the labels are never covered (and need no chip behind them; the spectrogram's frequency labels keep theirs).
    *Playhead glide:* a playhead move of more than 0.2 s in one frame (seek, ±5 s, back to start, a loop restarting) is drawn as a 260 ms ease-out glide from where it was towards the live position (display only — playback moves at once); the bars' light, the canvas skip zone and the spectrogram line all use the drawn position.
20. **Cover colours** ✅ — a track with a colourful cover takes its colour (`accent.rs`, `TrackInfo.accent`): the cover thumbnail's vivid pixels (saturation and value ≥ 0.3) are binned into 12 hue families weighted by saturation × value; of the two heaviest (the secondary only if ≥ 25 % of the primary), the brighter, more saturated mean colour wins, lifted for the dark UI (value ≥ 0.8, saturation 0.45–0.85). Saturation follows the cover (0.42–0.72). Other lanes keep the standard categorical palette.
